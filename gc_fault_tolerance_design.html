Section 01

Problem Statement

GlobalConductorV2 currently manages all active run execution state exclusively in JVM heap memory. When the application crashes or the EC2 instance is replaced, every in-flight run is silently lost — no recovery, no alert, no resume.

🔴
Critical Gap — No Crash Recovery

Any JVM crash, EC2 instance replacement, OOM kill, or forced restart causes ALL in-flight runIds to be permanently lost. The underlying external work (adapters, DAG operations, RDS) may still be running, but GlobalConductor has no way to re-attach to it after restart.

⚠️
Scenario: Mid-Adapter Crash

ADAPTER_MAIN sends SQS message. App crashes. Adapter finishes and puts result on output queue. Nobody reads it. Run is orphaned. DB shows STARTED forever.

⚠️
Scenario: Mid-SFW Crash

SFW thread is processing Steps 8–19. App crashes at Step 14. RDS is running, S3 bucket is partially marked. SFW never completes. pollElement() is gone. Run stuck as STARTED forever.

Section 02

State Audit — Memory vs. Persistent

A complete inventory of every piece of state the application maintains, classified by durability across a crash.

🔴 Volatile (Lost on Crash)
QueueService.inputBlockingResource ArrayBlockingQueue — runIds waiting for SFW thread. Capacity 50. Completely lost.
QueueService.outputBlockingResource ArrayBlockingQueue — completion signals. SFW thread's pollElement() loop broken.
QueueService.activeRuns ConcurrentHashMap.KeySet — set of in-flight runId strings.
ApiServiceDataManager.runIdApiServiceData mutable.Map — entire run plan (parallelApiList + sfwApiList + observer) per runId.
ApiObserverImpl.apiResultMap Map — in-memory mirror of step statuses. (DB has last written checkpoint.)
MetricRegisterUtil TrieMap Gauge metrics (start time, end time, adapter status). Lost — metrics go dark.
ReplayServiceDataManager.currentRunApisToProcess mutable.Map — replay step filter. Lost for any in-flight replay runs.
🟢 Durable (Survives Crash — PostgreSQL)
run_history table runId, Run_Status (STARTED/SUCCESS/FAILED), User_Name, Environment, Region, DVN, Input_Json (full request payload), Failed_API, Error_Message.
steps_history table Per-step status written on EVERY state change via ApiObserverImpl. Columns: run_id, api_name, step_status, step_message, start_time, end_time.
application_data table Adapter SQS output messages keyed by (runId, "AWS_SQS_MSG"). Written BEFORE deleting from SQS. This is the adapter completion durable record.
✅
Key Recovery Insight

The DB already contains everything needed for recovery: Input_Json has the full original request to reconstruct ApiData. steps_history has the last known status of every step. application_data has the adapter completion result. No new persistence layer is needed — only a startup routine to reconstruct in-memory state from these three tables.

Section 03

Adapter SQS Queue Flow — The Bridge to Recovery

Understanding the exact two-queue adapter messaging architecture is critical to designing correct crash recovery. The system's design already provides durable adapter state.

End-to-End Adapter Messaging Architecture

💡
Why This Design Already Works for Recovery

receivedAwsSQSMessage() deliberately stores the SQS message in DB before deleting it from SQS. This means after any crash, processSqsMessages() can always find the adapter result in the DB. The ADAPTER_STATUS_CHECK step with retryCount=-1 is inherently idempotent and crash-resilient.

Section 04

Crash Scenarios — Analysis & Recovery Action

Five concrete crash scenarios covering both pipeline phases, showing the DB state at crash time and the exact recovery action on restart.

A1
Adapter Phase Crash — Adapter Still Running
App crashes while ADAPTER_STATUS_CHECK is polling. Adapter has not yet finished.
DB STATE AT CRASH TIME:
ADAPTER_MAIN = SUCCESS ADAPTER_STATUS_CHECK = IN_PROGRESS / RETRYING application_data → empty SQS OUTPUT → empty
→
On restart: steps_history shows ADAPTER_MAIN = SUCCESS → adapter was invoked
→
application_data has no entry for runId → adapter hasn't responded yet
→
Recovery action: Rebuild ApiServiceData → resume from ADAPTER_STATUS_CHECK
→
receivedAwsSQSMessage() polls SQS → empty → no-op. processSqsMessages() reads DB → empty → FAILED → retry in 120s
→
Loop continues until adapter posts result to SQS OUTPUT → picked up → DB stored → COMPLETED/FAILED
🔄 Outcome: Automatically re-attaches to running adapter. Zero manual intervention.
A2
Adapter Phase Crash — Adapter Completed (Result on SQS or in DB)
Adapter finished and posted result. App crashed before or after consuming the SQS message.
DB STATE AT CRASH TIME (two sub-cases):
Sub-case A2a — Message still on SQS
ADAPTER_MAIN = SUCCESS ADAPTER_STATUS_CHECK = IN_PROGRESS application_data → empty SQS OUTPUT → has message
Crash happened before receivedAwsSQSMessage() ran. Message is still on SQS.
Sub-case A2b — Message already in DB
ADAPTER_MAIN = SUCCESS ADAPTER_STATUS_CHECK = IN_PROGRESS application_data → has COMPLETED message SQS OUTPUT → empty (already deleted)
Crash happened after SQS was read+deleted but before step marked SUCCESS.
→
Both sub-cases: Recovery action is identical — resume from ADAPTER_STATUS_CHECK
→
A2a: receivedAwsSQSMessage() reads from SQS → stores in DB → deletes from SQS → processSqsMessages() returns SUCCESS immediately
→
A2b: receivedAwsSQSMessage() finds nothing on SQS → no-op. processSqsMessages() reads DB → finds COMPLETED → returns SUCCESS immediately
→
Remaining parallel steps (START_GC1_API, WRITE_TO_INPUT_QUEUE) execute → run moves to SFW phase
✅ Outcome: Run continues to SFW phase without any re-invocation of adapter.
A3
Adapter Phase Crash — ADAPTER_MAIN Not Confirmed
App crashed while ADAPTER_MAIN itself was executing (SQS message may or may not have been sent).
ADAPTER_MAIN = IN_PROGRESS / RETRYING ADAPTER_STATUS_CHECK = WAITING application_data → check first
→
On restart: Check application_data for runId
→
If message exists in DB: Adapter was actually invoked and completed → resume from ADAPTER_STATUS_CHECK → reads DB → result
→
If no message in DB and no message on SQS OUTPUT: Cannot confirm adapter was invoked → FAIL SAFE: mark run as FAILED → send Webex alert → operator manually retries via replay endpoint
⚠️
Why Fail-Safe?

Re-invoking ADAPTER_MAIN blindly risks duplicate SQS INPUT messages → adapter processes the run twice → data corruption. It is always safer to alert the operator for manual replay.

S1
SFW Phase Crash — In Queue, Not Started
All adapter steps SUCCESS. Run is in inputBlockingQueue waiting for SFW thread.
Steps 0–7 = SUCCESS Steps 8–19 = WAITING
→
Most recoverable case. Rebuild ApiServiceData → put into inputBlockingQueue → SFW thread picks it up and runs Steps 8–19.
✅ Full recovery — no steps lost
S2
SFW Phase Crash — Mid Execution
SFW thread was processing Steps 8–19. Crash at some step N.
Steps 0–N = SUCCESS Step N+1 = IN_PROGRESS Steps N+2..19 = WAITING
→
Rebuild ApiServiceData → put into inputBlockingQueue. Already-SUCCESS steps are SKIPPED via status check. Execution resumes from Step N+1.
✅ Resume from last checkpoint
Section 05

Recovery Service Design

A startup-time recovery service that queries the DB, classifies each interrupted run, and reconstructs the exact in-memory state needed to resume execution.

Recovery Decision Tree

Modified Startup Sequence — Main.scala

Step 1
initLoggingModule() + initMonitoringModule() + initCryptoUtil()
Unchanged. Infrastructure setup.
Step 2
initHttpServer()
Unchanged. HTTPS server starts accepting requests. Recovery runs before SFW thread, not before HTTP.
Step 3 — NEW
StartupRecoveryService.recover()
Queries DB for STARTED runs. Classifies each. Rebuilds ApiServiceData. Routes to correct queue. Sends Webex summary. Completes before SFW thread starts.
Step 4
startSfwServiceThread()
Unchanged. SFW thread starts — immediately finds recovered runs in inputBlockingQueue and begins processing.
Section 06

Implementation Plan

Minimal, surgical changes. No new infrastructure. No new DB tables. No new queues. Pure code additions leveraging existing persistence.

NEW recovery/StartupRecoveryService.scala
  • Called from Main.main() before startSfwServiceThread()
  • Queries run_history for all STARTED runs older than configured threshold (e.g., 30 min)
  • For each run: reads steps_history, classifies phase, routes to recovery path
  • Sends Webex summary: "X runs recovered, Y runs marked FAILED"
  • Handles the case where no interrupted runs exist (normal startup) — no-op
// Pseudocode — key logic
object StartupRecoveryService {
  def recover(): Unit = {
    val interruptedRuns = StorageDataSource.getInterruptedRuns()
    interruptedRuns.foreach { run =>
      val phase = RecoveryPhaseDetector.detect(run.runId)
      phase match {
        case SfwPhase      => recoverSfw(run)      // put in inputBlockingQueue
        case AdapterPhase  => recoverAdapter(run)  // resume ADAPTER_STATUS_CHECK
        case Unrecoverable => markFailed(run)      // ADAPTER_MAIN uncertain
      }
    }
  }
}
NEW recovery/RecoveryPhaseDetector.scala
  • Reads steps_history for a runId and classifies the recovery phase
  • Returns sealed trait: AdapterPhase | SfwPhase | Unrecoverable
  • AdapterPhase: ADAPTER_MAIN=SUCCESS, ADAPTER_STATUS_CHECK not SUCCESS
  • SfwPhase: All Steps 0–7 are SUCCESS or SKIPPED
  • Unrecoverable: ADAPTER_MAIN = IN_PROGRESS/RETRYING AND no message in application_data
NEW recovery/ApiDataReconstructor.scala
  • Parses Input_Json column from run_history back to ApiData object
  • Rebuilds ApiServiceData with full parallelApiList and sfwApiList (same as ProcessRequest)
  • Registers reconstructed ApiServiceData in ApiServiceDataManager
  • Marks already-completed steps so they are SKIPPED during re-execution
MODIFIED database/StorageDataSource.scala
  • Add getInterruptedRuns(): SELECT from run_history WHERE Run_Status='STARTED' AND insert_time < NOW() - INTERVAL '30 minutes'
  • Returns List of (runId, inputJson, environment) tuples
  • Reuses existing retry(3, 30000) pattern for DB resilience
MODIFIED Main.scala
  • Add single line: StartupRecoveryService.recover() between initHttpServer() and startSfwServiceThread()
  • No other changes needed
def main(args: Array[String]): Unit = {
  initLoggingModule()
  initMonitoringModule()
  initCryptoUtil()
  initHttpServer()
  StartupRecoveryService.recover()   // ← NEW
  startSfwServiceThread()
}

📋
What We Are NOT Changing

No new database tables. No new AWS infrastructure (no DynamoDB, no ElastiCache). No changes to QueueService, ApiConductor, ApiObserverImpl, or any existing execution paths. No changes to the HTTP API surface. The existing replay mechanism is preserved and continues to work for manual recovery scenarios.

Executive Summary

GlobalConductorV2 stores all three pieces of information needed for crash recovery already: the full request payload (Input_Json), per-step execution status (steps_history), and adapter completion results (application_data). The proposed StartupRecoveryService adds a startup routine that reads these tables, reconstructs the in-memory run state, and re-queues interrupted runs — without changing any execution logic, without new infrastructure, and without risk of duplicate adapter invocations.
