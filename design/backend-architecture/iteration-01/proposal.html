1. Problem Statement

What problem does this feature solve?

The Bookkeeping app has a fully built React frontend but zero backend infrastructure. All data (contacts, transactions, user state) is either hardcoded in types.ts as initialContacts or managed ephemerally in React component state via useState. Nothing persists across page refreshes. The app is a non-functional UI shell.

Why does this problem matter?

  • Users cannot create real accounts, add real contacts, or record real transactions
  • No multi-user support — every user sees the same hardcoded data
  • No persistence — refreshing the browser erases everything
  • No deployment — the app only runs on localhost
  • No path to Pi Network integration without a server-side payment completion endpoint

What is the current behavior?

User opens the app → sees hardcoded contacts (Chengdiao Fan, Nicolas Kokkalis, etc.) → can add entries in-memory → refresh browser → all data lost. Guest mode and "Connect Pi Wallet" both lead to the same in-memory state with no server interaction.

What is the impact of not solving this?

The app remains a static demo with no real-world utility. Pi Network integration (Phase 4) is impossible without a backend to handle server-side payment approvals. The app cannot launch.

2. Goals

  1. G1: Persist all user, contact, and transaction data in a PostgreSQL database — verified by data surviving across browser refreshes and server restarts
  2. G2: Serve a REST API that the existing React frontend can consume, replacing all hardcoded/mock data — verified by zero hardcoded data in the shipped frontend
  3. G3: Support multi-user isolation — each Pi wallet address = one user account. Verified by two users seeing different data
  4. G4: Deploy the frontend to a CDN (Vercel) and backend to a managed platform (Railway) with the database accessible via connection string — verified by public URL accessibility
  5. G5: Design the auth layer to be swappable — temporary wallet-based auth (Phases 1-3) cleanly replaceable with Pi OAuth + JWT (Phase 4) — verified by auth middleware accepting a strategy pattern
  6. G6: Validate all API inputs with Zod schemas — verified by invalid requests returning 400 with descriptive errors
  7. G7: Add idempotency protection for transaction creation — verified by duplicate POST requests not creating duplicate records

3. Non-Goals

  • NG1: Real Pi Network SDK integration — deferred to Phase 4. This proposal designs the hooks for Pi SDK but does not implement them.
  • NG2: Real-time WebSocket updates — deferred to Phase 5. Polling is acceptable for Phase 1-3.
  • NG3: Offline support / PWA — out of scope for this iteration.
  • NG4: Mobile native app — the app is web-only (Pi Browser compatible).
  • NG5: Multi-currency support — Pi only.
  • NG6: Admin dashboard / back-office — not needed yet.

5. Proposed Behavior

Add a Node.js + Express + TypeScript backend that serves REST APIs, persists data in PostgreSQL via Prisma ORM, and is deployed on Railway. The frontend is deployed on Vercel and communicates with the backend over HTTPS.

6.3 Database Choice Analysis

Decision: Railway PostgreSQL

The bookkeeping_full_stack_plan.md listed Supabase as a placeholder. After deep analysis of the 4 options:

CriteriaSupabaseRailway PostgreSQLMongoDB AtlasSQLite
Data model fit✅ Relational✅ Relational⚠️ Document (forced for relational data)✅ Relational
Vendor lock-in⚠️ Supabase-specific APIs (RLS, Realtime, Auth)✅ Standard PostgreSQL — zero lock-in⚠️ MongoDB query language✅ Standard SQL
Cost✅ Free tier (500MB, pauses after 1 week inactivity)✅ $5/mo after trial (always-on)✅ Free 512MB✅ Free
Multi-user concurrency✅ Good✅ Good✅ Good❌ Single-writer, no concurrent access
Prisma compatibility✅ Works (needs directUrl)✅ Native — single DATABASE_URL⚠️ Prisma MongoDB adapter (less mature)✅ Works
Tooling (PgAdmin/DBeaver)⚠️ Must connect externally✅ Direct connection string — works with PgAdmin, DBeaver, psql❌ Different tooling (Compass)⚠️ Local file only
Backend co-location❌ Separate service✅ Same Railway project — low latency❌ Separate❌ Embedded only
Production readiness✅ Managed✅ Managed✅ Managed❌ Not for production

Why Railway PostgreSQL wins:

  1. User's preference — explicitly asked for Railway or PgAdmin/DBeaver compatible tooling
  2. Zero vendor lock-in — standard PostgreSQL, works with any ORM, any tool, portable anywhere
  3. Co-located with backend — both Express server and PostgreSQL run in the same Railway project, minimizing network latency
  4. Simpler Prisma config — single DATABASE_URL, no need for directUrl workaround
  5. Full PgAdmin/DBeaver support — user can connect with any SQL client for debugging and manual queries
  6. No pausing — Supabase free tier pauses after 1 week of inactivity, Railway stays on

Tradeoff: We lose Supabase's built-in Auth and Realtime features. But since Pi Network OAuth is the final auth (Phase 4), Supabase Auth would be throwaway work. Realtime (Phase 5) can be added via polling or WebSockets later.

  id              String        @id @default(cuid())
  piWalletAddress String        @unique
  piUsername       String?       @unique
  piUid           String?       @unique
  displayName     String        @default("Pioneer User")
  createdAt       DateTime      @default(now())
  updatedAt       DateTime      @updatedAt
  contacts        Contact[]
  transactions    Transaction[]

  @@index([piWalletAddress])
}

model Contact {
  id              String        @id @default(cuid())
  name            String
  category        String        // "individual" | "business"
  piWalletAddress String
  userId          String
  user            User          @relation(fields: [userId], references: [id], onDelete: Cascade)
  transactions    Transaction[]
  createdAt       DateTime      @default(now())
  updatedAt       DateTime      @updatedAt

  @@unique([userId, piWalletAddress])
  @@index([userId])
}

model Transaction {
  id             String    @id @default(cuid())
  description    String
  amount         Float
  type           String    // "credit" | "debit"
  source         String    @default("manual")
  txHash         String?
  piPaymentId    String?
  idempotencyKey String?   @unique
  timestamp      DateTime  @default(now())
  userId         String
  user           User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  contactId      String?
  contact        Contact?  @relation(fields: [contactId], references: [id])

  @@index([userId])
  @@index([userId, contactId])
  @@index([userId, timestamp])
  @@index([idempotencyKey])
}

7.3 Key Schema Decisions

  • idempotencyKey added to Transaction — prevents duplicate transaction creation from network retries or double-clicks. Frontend generates a UUID per form submission.
  • Composite unique constraint on [userId, piWalletAddress] in Contact — a user cannot add the same wallet address twice as a contact.
  • Cascade delete on User→Contact and User→Transaction — deleting a user removes all their data (GDPR-friendly).
  • Indexes on userId, [userId, contactId], and [userId, timestamp] — optimizes the most common queries (list contacts for user, ledger for contact, sorted transactions).
  • Float for amount — Pi amounts are fractional. For a bookkeeping app (not a bank), Float precision is acceptable. If sub-satoshi precision is needed later, switch to Decimal.
  • No directUrl needed — Railway PostgreSQL uses a single connection string (unlike Supabase which needs both pooled and direct URLs).

11. Auth & Security

11.1 Phase 1-3: Wallet-Based Header Auth

// backend/src/middleware/auth.ts
export async function walletAuth(req, res, next) {
  const walletAddress = req.headers['x-wallet-address'];
  if (!walletAddress) {
    return res.status(401).json({ error: 'UNAUTHORIZED', message: 'Missing x-wallet-address header' });
  }
  const user = await prisma.user.findUnique({ where: { piWalletAddress: walletAddress } });
  if (!user) {
    return res.status(401).json({ error: 'UNAUTHORIZED', message: 'User not found' });
  }
  req.user = user;
  next();
}

Security assessment: This is intentionally insecure. Any client can impersonate any user by setting the header. This is acceptable for Phase 1-3 (development/staging) because:

  • No real money is involved — Pi SDK is not integrated yet
  • The app is in development — not public
  • The middleware is designed as a strategy pattern — swapped to JWT in Phase 4

11.2 Phase 4: Pi OAuth + JWT

// Phase 4 replacement
export async function jwtAuth(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'UNAUTHORIZED' });
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.user = await prisma.user.findUnique({ where: { id: payload.userId } });
    if (!req.user) return res.status(401).json({ error: 'UNAUTHORIZED' });
    next();
  } catch (e) {
    return res.status(401).json({ error: 'TOKEN_EXPIRED' });
  }
}

11.3 Security Measures (All Phases)

  • CORS — whitelist only localhost:5173 (dev) and bookkeeping.vercel.app (prod)
  • Rate limiting — 100 requests/minute per IP (general), 10 requests/minute for write endpoints
  • Input validation — Zod on every endpoint, no raw user input reaches DB
  • SQL injection — prevented by Prisma (parameterized queries)
  • User isolation — every query includes WHERE userId = req.user.id
  • Helmet.js — set security headers (X-Content-Type-Options, X-Frame-Options, etc.)

13. Concurrency & Thread Safety

13.1 Transaction Creation

Risk: Two identical requests arrive simultaneously (double-click, network retry).

Mitigation: The idempotencyKey field has a unique constraint. If two INSERT statements race, PostgreSQL's unique constraint will reject the second one. The API returns the existing transaction in the 409 response.

13.2 Contact Creation

Risk: User tries to add the same wallet address twice.

Mitigation: The @@unique([userId, piWalletAddress]) constraint on Contact prevents duplicates at the database level.

13.3 User Upsert

Risk: Two requests for the same wallet address hit GET /api/users/:walletAddress simultaneously, both trigger INSERT.

Mitigation: Use Prisma's upsert which translates to INSERT ... ON CONFLICT DO UPDATE — safe under concurrency.

13.4 Balance Summary

Risk: A transaction is created between the SUM(credit) and SUM(debit) queries.

Mitigation: Use a single SQL query with conditional aggregation: SUM(CASE WHEN type='credit' THEN amount ELSE 0 END) — atomic read.

14. Failure Handling & Recovery

14.1 Database Unavailable

If PostgreSQL is unreachable, Prisma throws a PrismaClientKnownRequestError. The global error handler catches it and returns 503 Service Unavailable. The frontend shows a "Server is temporarily unavailable" toast. No data corruption — the transaction never started.

14.2 Backend Crash Mid-Request

Each API request is a single database operation (INSERT or SELECT). There are no multi-step transactions in Phase 1-3. If the server crashes between receiving the request and responding, the operation either completed (committed to DB) or didn't (no partial state).

14.3 Network Error (Frontend ↔ Backend)

The API client wraps all calls in try/catch. On network error, it shows a toast and does NOT retry automatically (to avoid duplicate writes). The user can manually retry. Idempotency keys protect against accidental duplicates.

14.4 Phase 4: Pi Payment Failure

Pi payments are a multi-step process (create → approve → complete). If the server crashes between steps, the pending transaction remains in pending state. A background job (or manual admin action) can reconcile pending transactions by querying the Pi Platform API for their status.

17. Performance Impact

17.1 Expected Load

Early-stage app — expect <100 users, <1000 requests/day. Performance is not a concern initially.

17.2 Potential Bottlenecks

  • Summary endpoint — GET /api/transactions/summary does a full aggregation. With indexes on [userId, timestamp], this is fast up to ~100K transactions per user.
  • Pagination — offset-based pagination (OFFSET + LIMIT) degrades for high page numbers. Switch to cursor-based pagination if needed.
  • Connection pool — Prisma defaults to 10 connections. Railway PostgreSQL free tier allows ~20. Sufficient for Phase 1-3.

17.3 Cold Start

Railway free tier may sleep the container after inactivity. First request after sleep incurs ~2-3s cold start. Mitigation: Railway's paid tier ($5/mo) keeps the container warm.

20. Assumptions

  1. A1: Users have unique Pi wallet addresses — no shared wallets.
  2. A2: Pi wallet addresses are stable identifiers — they do not change over time.
  3. A3: The app will have <1000 users in the first 6 months — no need for horizontal scaling initially.
  4. A4: Railway PostgreSQL free tier (or $5/mo) is sufficient for early-stage storage needs.
  5. A5: Pi Network SDK will be available and functional for Phase 4 — the sandbox API works as documented.
  6. A6: The frontend can be modified to send an x-wallet-address header on all API calls without significant refactoring.
  7. A7: Float precision for Pi amounts is acceptable — Pi does not require sub-decimal precision beyond 2-3 decimal places.
  8. A8: Users will primarily access the app via Pi Browser or mobile Chrome — desktop usage is secondary.
  9. A9: CORS whitelist of the Vercel domain is sufficient security for Phase 1-3 (no real money involved).
  10. A10: Railway's built-in HTTPS is sufficient — no need for custom SSL certificates.

D-001 Railway PostgreSQL over Supabase User preference for PgAdmin/DBeaver compatibility, zero vendor lock-in, co-located with backend, simpler Prisma config, no free-tier pausing Supabase (built-in auth/realtime but lock-in), MongoDB Atlas (document model poor fit for relational data), SQLite (no multi-user)

D-003 Prisma over Drizzle/Knex/raw SQL Type-safe, auto-migration, matches plan Drizzle (lighter but less mature), Knex (no type safety), raw SQL (error-prone)
D-004 Monorepo (npm workspaces) over separate repos Shared types, single deploy, matches plan Separate repos (more isolation but shared types become a pain)
D-005 Idempotency key on transactions Prevents duplicate transactions from retries/double-clicks — critical for a payment app No idempotency (simpler but risky), database-level dedup (harder to implement)
D-006 Wallet header auth for Phase 1-3 Fastest path to a working app; no real money involved; cleanly replaceable with JWT JWT from day 1 (more secure but premature complexity), no auth (even more insecure)
D-007 Defer Pi SDK to Phase 4 Build the complete app first, then integrate Pi. Reduces risk of SDK-related blockers. Integrate Pi SDK first (risky — SDK issues could block all development)
