Following design-verification-skill.md: independently verify every proposed fix from iteration-01, construct compound scenarios, and render a verdict.

Critical Issue Verification

G-001: Session Token Auth VERIFIED

Issue: Wallet header allows impersonation

Fix: Session table with UUID tokens, Bearer header, 24h TTL

Verification:

  1. Can an attacker guess a session token? UUID v4 has 122 bits of randomness. Brute-force is infeasible (~5.3 x 10^36 possibilities). ✅
  2. Can a token be reused after expiry? Middleware checks expiresAt < NOW(). Expired tokens are rejected with 401. ✅
  3. Can an attacker steal a token? Tokens are in localStorage (XSS risk, but mitigated by G-005 XSS sanitization). Same risk as JWT. ✅ with caveat
  4. Can two sessions exist for the same user? Yes, by design (multiple devices). Each session is independent. ✅
  5. Session cleanup? No cleanup mechanism for expired sessions. ⚠️ Minor: add periodic cleanup, but non-blocking.

Verdict: ✅ VERIFIED — significantly better than raw wallet header. Session token theft via XSS is the residual risk, mitigated by G-005 and React's default escaping. Phase 4 JWT eliminates this.

G-006: Simultaneous Payments VERIFIED

Fix: Independent transactions, reconciliation job

Verification: Walked through the scenario: User A pays B 100π, B pays A 50π simultaneously.

  1. Two independent rows in Transaction table with status=pending. No shared state. ✅
  2. No database lock contention (different rows, different IDs). ✅
  3. If A's completes but B's fails, ledger shows both correctly (one completed, one failed). ✅
  4. Reconciliation job handles both independently. ✅

Verdict: ✅ VERIFIED — no coupling between independent payments.

G-009: Decimal Precision VERIFIED

Fix: Decimal @db.Decimal(18,7)

Verification:

  1. Storage: PostgreSQL NUMERIC(18,7) is exact. 0.1 + 0.2 = 0.3 exactly. ✅
  2. Prisma → JS: Prisma returns Decimal as string ("150.5000000"). API must parseFloat(). Does this lose precision? parseFloat("0.1234567") === 0.1234567 — yes, JS float has ~15 significant digits, 7 decimal places is safe. ✅
  3. Aggregation: PostgreSQL SUM on NUMERIC stays NUMERIC. No precision loss in the DB. ✅
  4. Frontend display: JS receives a number. toFixed(2) or toFixed(7) for display. No issue. ✅

Verdict: ✅ VERIFIED — Decimal is correct and the Prisma→JS→frontend pipeline preserves precision for 7 decimal places.

G-018: Required Idempotency Key VERIFIED

Fix: idempotencyKey: z.string().uuid() (required)

Verification:

  1. Double-click: Same UUID sent twice. Second INSERT fails on unique constraint. API returns 409 with existing tx. ✅
  2. Network retry: Same UUID. Same result. ✅
  3. Frontend generates UUID on form render, not submit: Ensures retries use same key. ✅
  4. What if frontend sends empty string? Zod z.string().uuid() rejects it (400 error). ✅
  5. What if frontend reuses key across different transactions? The key is unique globally. If reused, the second different transaction is rejected as duplicate. This is correct behavior — force the frontend to generate a new key per form. ✅

Verdict: ✅ VERIFIED

G-023: Pending TX TTL + Reconciliation VERIFIED

Fix: 30-min TTL, cron job every 5 min, checks Pi Platform API

Verification:

  1. User closes browser after 10 min: TX stays pending. After 30 min, cron job finds it, checks Pi API. If payment went through on blockchain, updates to completed. If not, updates to expired. ✅
  2. Pi API is down during reconciliation: Cron job skips that TX, tries again in 5 min. No data corruption. ✅
  3. Concurrent reconciliation jobs: Railway runs one instance. No concurrent cron executions. ✅
  4. What if payment completes AFTER we mark it expired? Edge case: user approves at minute 31, blockchain confirms at minute 32. Our DB says expired. Pi API says completed. Next cron run should re-check and update. But the reconciliation only checks status=pending AND expiresAt < NOW(). If we already set status=expired, we won't re-check. ⚠️

New issue found:

V-001: Reconciliation should also check status=expired transactions that are < 1 hour old against Pi API, in case the blockchain confirmed after our TTL. Severity: MAJOR

Mitigation: Add a second reconciliation pass: WHERE status='expired' AND expiresAt > NOW() - INTERVAL '1 hour'. If Pi API says completed, update to completed.

Verdict: ⚠️ PARTIALLY VERIFIED — core mechanism works, but V-001 needs addressing for Phase 4.

Compound Stress Test Scenarios

Scenario 1: Session token + XSS attack

Attacker creates a transaction with description <script>fetch('/api/...',{headers:{Authorization:document.cookie}})</script>

Step 1: Zod transform runs xss() → strips all HTML tags → stored as plain text
Step 2: Even if sanitization fails, React escapes on render
Step 3: Session tokens are in localStorage, not cookies → document.cookie is empty
Result: ✅ PASS — three layers of defense

Scenario 2: Double-click + network timeout + server crash

User clicks "Add Entry" twice rapidly. First request hits server, server crashes after INSERT but before response. Second request arrives at restarted server.

Step 1: First request: INSERT succeeds (committed to DB), response lost
Step 2: Frontend retries with same idempotencyKey
Step 3: Server checks unique constraint → finds existing row → returns 409 with existing tx
Step 4: Frontend treats 409 as success (idempotent)
Result: ✅ PASS — exactly one transaction created

Scenario 3: User A creates transaction with User B's contactId + pool exhaustion

User A sends POST /api/transactions with contactId belonging to User B. Simultaneously, connection pool is nearly exhausted.

Step 1: Auth middleware validates session token → attaches req.user (User A)
Step 2: Controller calls findFirst({ id: contactId, userId: req.user.id })
Step 3: Contact not found for User A → returns 404
Step 4: If pool exhausted during findFirst, Prisma throws P2024 → global handler returns 503
Result: ✅ PASS — no cross-user data leak, graceful degradation under load

Scenario 4: Pi payment approved on blockchain after TTL expiry

User approves payment at minute 29. Blockchain confirms at minute 32. Our TTL is 30 min.

Step 1: Cron job at minute 30 finds pending tx, checks Pi API → not yet confirmed → leaves as pending
Step 2: Cron job at minute 35 finds pending tx (expiresAt passed) → marks as expired
Step 3: Blockchain actually confirmed at minute 32
Step 4: Without V-001 fix: money debited from Pi wallet but our DB says expired. INCONSISTENCY.
Step 5: With V-001 fix: second reconciliation pass checks recently-expired txs against Pi API, updates to completed.
Result: ⚠️ CONDITIONAL PASS — requires V-001 fix for Phase 4

Scenario 5: Prisma migration adds required field + Railway deploy

Developer adds a NOT NULL column without default to a table with existing data.

Step 1: prisma migrate deploy runs during Railway build
Step 2: Migration fails: "column X cannot be NOT NULL with existing rows"
Step 3: Build fails. Railway keeps old container running. No downtime.
Step 4: Developer fixes: adds column as nullable, deploys, backfills, then adds NOT NULL constraint in second migration.
Result: ✅ PASS — Railway's blue-green deploy prevents data loss
