Why users type their own Pi wallet address

Decision record · Bookkeeping (Pi Network dApp) · Decided 19 Nov 2026 · Built on feature_branch/backend-implementation, not deployed yet

Decision: the app asks each user, once, for their own public Pi wallet address (Settings → Profile → Pi Wallet Address).

Why: Pi doesn't give apps the user's wallet address unless Pi has put the app on an allowlist. We tried every route live and got either no address or unauthorized_app.

Why we need it: the Pi blockchain only knows wallet addresses. Without the user's own address, the app can't tell which of a contact's payments were with this user. Before this change it imported the contact's payments with everyone.

Is it safe? A public wallet address is meant to be shared, like a UPI ID. It can receive Pi but can't be used to spend it. A wrong address only affects that user's own khata.

1. The problem, in one example

The Automatic screen reads a contact's payments from the Pi blockchain and adds them to the user's khata. In our test (Pi Testnet, 18 Sep → 18 Nov 2026), the test contact had 49 payments in the chosen dates:

  • 2 were with our test wallet: these belong in the khata.
  • 47 were the contact paying, or being paid by, other people. The old scan still added them as "Pi received from …".

To keep only the right ones, the app has to compare both ends of each payment with two addresses: the contact's (we already have it, because Add Contact requires one) and the user's own, which we didn't have.

5. Why option C

  1. It's the only option that works for every user today, without waiting on Pi.
  2. The address is public by design. Sharing it is like sharing a UPI ID to receive money. It can't be used to spend Pi.
  3. Low risk. A wrong address, or someone else's, only changes what that user's own khata imports. No one else's data is touched.
  4. One-time and quick: copy it from the Pi Wallet, paste, save.
  5. It keeps the better options open. If Pi allowlists us (B), the field can fill itself, and a Premium payment (D) can pre-fill it.

6. What was built (19 Nov 2026)

Settings → Profile → Pi Wallet Address

  • An Add my wallet address / Change wallet address button. Guests see the sign-in prompt instead.
  • Before saving, the app checks the format (G followed by 55 letters or digits; spaces and line breaks are removed) and that the address exists on Pi Testnet, which catches typos.
  • Stored on the server as User.walletPublicKey (a new optional column) through PUT /api/users/me/wallet. Only signed-in users can call it, and the rate limit counts per user. The address comes back with the user at every sign-in.

Automatic scan

The scan won't start without the user's address. It shows "Add your own Pi wallet address first" with an Open Settings button. When it runs, it reads Pi Testnet only, every page in the date range, and keeps only these payments:

Payment on the blockchainIn the khata
From the contact to youCredit: you received
From you to the contactDebit: you paid
Contact ↔ anyone else, or tokens other than PiSkipped

How it was checked

  • Real testnet data: 49 payments in range became 2 for the test wallet, matching an independent count. A wallet with no shared payments got 0 and a clear message. With no address saved, the scan is blocked.
  • Backend tests: new suite 11-user-wallet (13 checks: sign-in required, format, pasted spaces, per-user, clearing). All 140 checks pass.

8. Paying a contact without a middleman: ways forward

The same rule applies to the Pay button: money must go straight from the user's wallet to the contact's wallet. The app never holds it. Pi's SDK can't send to another user (Pi.createPayment only pays the app), so the actual "send" happens in the Pi Wallet. The app's job is to get the user there with everything filled in, then confirm the payment on the blockchain.

What we found in Pi's own code on 19 Nov 2026 (SDK, the Pi Browser host bundle and the wallet):

  • The wallet's send screen is wallet.pinet.com/pay-request. It reads publicKey (the recipient) and amount from the link. It does not read a memo.
  • The same link is Pi's official wallet QR-code format: https://wallet.pinet.com/pay-request?publicKey=G…&amount=10.
  • An app can open a pi:// or https:// link outside itself with Pi.openUrlInSystemBrowser(url). There's no allowlist for this. In the desktop sandbox it does nothing, so it can only be tested on a phone.
  • Pi.Wallet.signTransaction / submitTransaction (signing inside our app) only work for four of Pi's own apps (domains, ecosystem, tiramisu, launchpad), listed in the code. navigateHost is limited to Pi's ecosystem app.

Confirming a payment: Pi's public blockchain API (Horizon) lists each payment's sender, receiver, amount, asset, time and transaction hash, with the memo through join=transactions. It also supports live updates, so the app can see the payment arrive while the user is in the wallet.

10. Can the app pay through Pi's RPC server? (research, 19 Nov 2026)

Short answer: no, not on its own. The RPC server is a delivery service for the blockchain. It reads data and delivers transactions that are already signed. Moving Pi out of a wallet needs that wallet's secret key, and only the Pi Wallet holds it. The RPC server changes nothing about who can sign.

What the RPC server is

  • Pi launched a free public RPC server on Testnet in April 2026: https://rpc.testnet.minepi.com. It's the standard Stellar RPC server (Pi's chain is built on Stellar), made mainly for smart contracts.
  • We called it live on 19 Nov 2026: getHealth → "healthy", getNetwork → passphrase "Pi Testnet", protocol 30. It's the same Testnet blockchain our Horizon calls already read.
  • What it does: read accounts, balances and contract data; simulate a contract call; submit a transaction that is already signed (sendTransaction). What it doesn't do: sign anything, or move Pi for anyone.
1. Build the payment
(any app can)→2. Sign it with the payer's secret key
(only the Pi Wallet can)→3. Submit to the blockchain
(RPC server or Horizon)

The RPC server only helps with step 3, which we could already do through Horizon. Step 2 is the part Pi keeps inside the Pi Wallet, and that's the step that matters.

Option D in detail

Tap Pay→Pi popup in our app: user pays the app→Backend approves + completes→Backend sends app wallet → contact→Khata entry with both hashes
  • Secret key on our server: the backend must keep the app wallet's secret key, in Railway variables only, never in git.
  • We hold the user's money for a few seconds. If the second payment fails, we must retry it or refund the user, so it needs a retry job.
  • The blockchain shows "you → app → contact", not "you → contact". It also costs two network fees.
  • Mainnet: apps that hold and pass on users' money may break Pi's developer rules and can count as a payment service. We'd need to check with Pi before launch.
  • Size: a medium backend build (new payment type, app-wallet send, retry/refund, tests).

Note: the "contact must also use our app" limit in section 4 (option F) applies only to Pi's official app-to-user API. A plain blockchain payment from the app wallet can go to any address.

Recommendation: keep option E. Build D on Testnet only if the client decides that paying inside the app matters more than "straight from you to the contact", and accepts the trade-offs above. Never build A.

Horizon vs RPC: which one should the app use?

Both read and write the same Pi blockchain, but they're built for different jobs. Neither can sign a payment.

Horizon (what the app uses)RPC server
Made forPayments and account historySmart contracts
"All payments of this account"Yes One call, with paging and date orderNo No such call. You'd have to scan blocks yourself
How far backFull historyAbout 3 months. Its oldest data was from about 19 Aug 2026 when we checked on 19 Nov 2026
Smart contracts (simulate, events, contract data)NoYes
Submit a signed paymentYesYes
Sign a paymentNoNo
  • For this app, Horizon wins. Auto Sync and the Pay check need "payments between you and this contact, by date", which Horizon answers in one call. RPC can't, and it forgets anything older than about 3 months.
  • RPC wins only for smart contracts.
  • Overall: keep Horizon, and add RPC only if the app ever uses smart contracts. In the wider Stellar world new tools lean towards RPC, but on Pi, Horizon is fully live, so there's no reason to switch.

11. Explaining it to the client

The one-paragraph answer: "The RPC server lets apps read the blockchain and deliver payments, but every payment has to be signed by the owner's secret key first, and Pi keeps that key inside the Pi Wallet. No app can sign for the user, on Testnet or Mainnet. That's why Pay opens the Pi Wallet: it's the only place the payment can be signed. Apps that seem to pay inside themselves, like bnpi.app, are taking payment for their own service. Pi allows that, but not paying a third person."

A comparison that usually lands: the blockchain is like a bank's public ledger, and the RPC server is the bank counter. Anyone can look up an account or hand in a cheque at the counter. But the counter accepts only cheques the account owner has signed, and only the owner's own cheque book (the Pi Wallet) can sign one. Our app can fill in the cheque and take you to your cheque book; it can't sign it for you.

Questions he is likely to ask

He saysAnswer
"Pi launched an RPC server on Testnet, so we can send payments through it."The RPC server delivers signed payments. Signing needs the payer's secret key, which only the Pi Wallet has. We tested the server live: it works, and it accepts only signed transactions. It's the same as the Horizon API we already use.
"Blockchain data is public. Why can't we use it to move money?"Reading and spending are different. Anyone can see every balance and payment (that's how our Auto Sync works). Only the owner can spend, because spending needs their secret key.
"Then let the user type in their secret key or passphrase."No. That passphrase most likely also unlocks their real Mainnet Pi. Asking for it is what scam apps do, Pi would block us, and if our server were ever hacked, every user's Pi could be stolen.
"bnpi.app pays inside the app without opening the wallet."bnpi sells hotel bookings, so the user pays bnpi itself through Pi's in-app popup (Pi.createPayment). That popup can only pay the app's own wallet, never another person.
"So do it like bnpi: the user pays us, and we pay the contact."Possible on Testnet (option D). But we'd hold users' money, keep a wallet key on our server, pay two fees, and the history would show "you → app → contact". On Mainnet Pi may not allow it. It's a business decision, not a technical one. See section 10.
"The SDK has Pi.Wallet.submitTransaction."It needs a transaction that's already signed, and Pi enables these wallet calls only for four of Pi's own apps. For our app it returns unauthorized_app; we tested it.
"Use a smart contract on the RPC server."A contract still runs only when the user signs the call. The fingerprint unlock only works inside the screens Pi provides: the Pi Wallet's send screen (a plain payment to an address) and the in-app payment popup (which pays the app). Neither can sign a contract call, and the call that could (Pi.Wallet.signTransaction) is limited to Pi's own apps. Same wall.
"It's only Testnet, so the rules must be looser."Same rules: Testnet is a copy of the real network with test Pi. The signing works the same way, so there's no Testnet-only shortcut.
"Why does the user have to unlock with a fingerprint?"That's the Pi Wallet asking the owner to sign. It's the security that protects their Pi. Every legitimate wallet works this way, like UPI asking for your PIN in GPay.
"Will this ever change?"Possibly. We can apply to Pi to be allowlisted for Pi.Wallet.signTransaction, which would open the wallet over our app with everything filled in. Today only Pi's own apps have it, so we can't promise it.
