Which names Pi gives an app, and which it doesn't

Research record · Bookkeeping (Pi Network dApp) · 19 Nov 2026 · Evidence: our live sign-in tests (18–19 Nov 2026), the Pi SDK and Pi Browser code, Pi's developer docs, Pi's Privacy Policy and Developer Terms, and the source of other Pi apps.

Short answer. When a Pioneer signs in, an app like ours gets an app-specific id (uid) and the Pi username (for you: rohitagarwal2003). That is all. No sign-in scope or Platform API field gives a third-party app the user's legal name, real name or display name, or their email, phone number, photo or country. The only route to identity data is PiVerify, Pi's paid KYC service for businesses (section 5).

Pi does know your name. You gave it to Pi, and KYC checks it against your ID. Pi's own apps read it through Pi's internal API, which uses your own login: the Pi Browser menu, for example, shows a display name followed by @username. That data stays inside Pi.

So the "two names" you saw came from either a Pi app or an app where someone typed the name in. Our best move: keep the contact names users type (already built), and optionally let each user enter a display name, always shown next to their @username and never called "legal" or "verified".

1. What Pi returned when you signed in

We signed in with your Pi account in the Pi Sandbox on 18 and 19 Nov 2026 and logged exactly what came back. We asked Pi twice, in two different ways: the browser SDK call (Pi.authenticate) and our backend's call to Pi's Platform API (GET /v2/me). Both gave the same answer: an id and the username, plus technical fields such as when the sign-in expires. Nothing else about you.

2. Every scope an app can ask for

A scope is a piece of data or a permission an app asks for at sign-in. Pi shows the requested scopes on its consent screen. The Pi SDK only accepts a fixed list of seven, which is written in its code. Here is the full list, what the consent screen says for each, and what the app actually receives.

Outside the Pi Browser, Pi has a web sign-in (Pi.signIn, an OAuth page at /oauth/authorize on Pi's sign-in host). Its list is even shorter: username, roles, wallet_address, preferred_language, with username as the default. It has no name either.

Watch out: Pi's pi-sdk-js package declares a PiUser type with a name field, but its code only asks for payments and username, so that field is never filled.

3. Pi has your name, but keeps it inside Pi

Pi's Privacy Policy (updated 28 June 2026) says Pi collects contact and identity details such as your name, phone number, email, Facebook name and username. The Pi Browser's own code reads these through a separate, internal API (socialchain.app/api) using your own Pi login. That API has your first and last name, a display name, and your KYC status. Pi's screens use it: the side menu shows a display name followed by @username, the security circle shows display names, and there is even a privacy switch to hide your real name from your earning team.

Third-party apps never get that login. They only see the public door, the SDK plus /v2/me, and that door passes the uid and username, plus roles and language if the app asks for them and you allow it.

4. Why Pi doesn't share names

Pi doesn't publish a single reason. Its documents and design point the same way, though, and the reasons below are what we infer from them.

  • Names are KYC data. The name on a Pi account is checked against an ID during KYC, and Pi's help wiki says a name change must still describe the same person. That makes it sensitive personal data, not a profile nickname. likely
  • The Privacy Policy gives developers nothing. Its sharing section has no clause for passing personal data to app developers. KYC results go only to businesses using Pi's KYC service, and only with your consent. read
  • The Developer Terms point the same way. Developers may not collect information about Pi users without their consent, and may not pass on user ids, usernames or access tokens except to their own service providers. read
  • Each app gets a different uid for the same person. Pi's sign-in docs say this is so two apps can't link the same person. Sharing names would undo that. Pi docs
  • Users control who sees their full name. Pi's Social Profiles have a "full name visibility" setting; in Pi's own screenshot it is set to Private, visible only to you. Pi has said Social Profiles may become a developer resource "eventually"; it hasn't shipped. Pi blog

5. How apps that show two names do it

Every app we found that shows a name next to the username uses one of three patterns. Only the first gets the name from Pi.

Which case did you see? If you, or the other person, typed the name into that app, it was pattern B. If the name appeared without anyone typing it, it was a Pi app (pattern A): the Pi Browser menu, a Social Profile, Fireside Forum (Pi says Social Profiles were integrated there; we didn't verify that it shows full names) or the security circle. A third-party app can't show a name nobody typed.

6. Where our app stands today

We traced every name our app shows back to its source. Two findings matter for this decision. Neither was changed as part of this research.

  • The "Legal Name" label is wrong, and the pencil edit makes it worse. In Settings → Profile, the Display Name, "Legal Name" and "Username" rows all come from one value that starts as the Pi username (src/components/Settings.tsx). If you change the Display Name to "Rohit Agarwal", the screen shows "Legal Name: Rohit Agarwal" and "Username: @rohit_agarwal", both tagged "From Pi Auth", and neither is true. The edit isn't saved, so it is gone after a reload.
  • Most of a display-name feature already exists. The Profile screen has a Display Name field with a pencil edit and an info note ("visible to other users of this dApp in the future"). The backend has User.displayName (default "Pioneer User") and an owner-only PUT /api/users/:walletAddress that accepts 1–100 characters and strips HTML. usersApi.updateProfile exists in src/lib/api.ts, but nothing calls it. User.piUsername exists and is never set.

8. Recommended next step: an optional display name

This is a suggestion; nothing has been built yet. The Profile field, the database column and the update endpoint already exist, so the work is mainly connecting them. One small backend change is needed: today the name can't be cleared (the column defaults to "Pioneer User" and the endpoint needs at least 1 character), so making it optional means a nullable column (one small migration) and letting the endpoint accept an empty name.

Rules to follow if we build it

  • Never claim it is real. No "legal", "verified" or tick icon next to a typed name.
  • Always show @username next to it. Anyone can type "Pi Core Team" as a name; the username, which Pi provides, is what identifies the person. Pi's own side menu also shows the name followed by @username.
  • Keep it optional, editable and clearable, and mention it in the privacy notice. Cap it at about 60 characters (today's limit is 100) and reject links; sanitizedString already strips HTML.
  • Don't share it. The Developer Terms restrict passing user ids and usernames to anyone but our own service providers; treat the display name the same way.
