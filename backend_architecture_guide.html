2. Full-Stack System Architecture

The application follows a clean 3-tier architecture with clear separation of concerns:

Layer Primary Files Core Responsibility
Client src/lib/api.ts, src/App.tsx Manages user UI state, triggers API requests with stored Bearer token, handles automatic logout on 401.
API Gateway / Middleware backend/src/index.ts, backend/src/middleware/* Enforces CORS, security headers, rate limits (read 100/min, write 30/min), body parsing limit (100kb), and error handling.
Auth Layer backend/src/middleware/auth.ts Extracts Authorization: Bearer <token>, queries Session table, checks expiration, attaches req.user.
Business Logic backend/src/controllers/* Handles transactions, idempotency checks, contact aggregation queries, profile updates.
ORM & Database backend/prisma/schema.prisma, backend/src/lib/prisma.ts Defines models, relational integrity (cascades, setNull), migrations, and executes parameterized SQL.
Background Daemon backend/src/jobs/reconciliation.ts Runs every 5 minutes: auto-reconciles pending Pi payments and purges stale sessions from database.

3. Request Lifecycle & Codeflow

Every HTTP request follows a strict, predictable pipeline from arrival at Express to database query and formatted JSON response.

Code Architecture Breakdown

  • Entry Point (backend/src/index.ts): Initializes Express, attaches security middlewares (Helmet, CORS, Pino HTTP logger), mounts sub-routers, registers 404 & 500 error handlers, and listens on port 3001. Handles SIGINT and SIGTERM for zero-downtime graceful shutdown.
  • Configuration (backend/src/lib/config.ts): Enforces strict environment variable presence. Fails fast at startup if critical variables like DATABASE_URL are missing.
  • Validation (backend/src/middleware/validate.ts): Intercepts request payloads and runs them against Zod schemas. Strips dangerous HTML tags via xss to prevent stored Cross-Site Scripting (XSS).
  • Serializers (backend/src/lib/serializers.ts): Converts internal Prisma objects (like Prisma.Decimal amounts and ISO Dates) into standard JSON numbers and strings expected by the React frontend.

4. Database Architecture & Prisma ORM

The persistence layer runs on PostgreSQL managed through Prisma 5.x. The schema ensures data integrity through strict foreign keys, cascading deletes, and unique compound constraints.

Key Database Design Highlights

Design Choice Implementation Engineering Rationale
Currency Precision Decimal(18, 7) Standard floating-point numbers suffer from rounding errors (e.g. 0.1 + 0.2 = 0.30000000000000004). Decimal(18, 7) provides exact 7 decimal places for crypto micro-transactions.
Soft Deletion deletedAt DateTime? When a transaction is deleted, the record is not dropped. deletedAt is stamped. This preserves audit trails and prevents financial discrepancies.
Contact FK Rule onDelete: SetNull Deleting a contact will never delete the underlying financial transactions! The transaction simply sets its contactId = null, preserving accurate wallet balances.
Single-Query Grouping $queryRaw with LEFT JOIN Resolves the N+1 database problem. When listing contacts, totals (credit, debit, last transaction timestamp) are aggregated in a single SQL query on the database engine.
View High-Performance Contact Aggregation SQL OPTIMIZED 
SELECT
  c.id, c.name, c.category, c."piWalletAddress", c."userId",
  c."createdAt", c."updatedAt",
  COALESCE(SUM(CASE WHEN t.type = 'credit' THEN t.amount ELSE 0 END), 0)::float AS "totalCredit",
  COALESCE(SUM(CASE WHEN t.type = 'debit'  THEN t.amount ELSE 0 END), 0)::float AS "totalDebit",
  MAX(t.timestamp) AS "lastSeen"
FROM "Contact" c
LEFT JOIN "Transaction" t
  ON t."contactId" = c.id
  AND t."userId" = ${userId}
  AND t."deletedAt" IS NULL
WHERE c."userId" = ${userId}
GROUP BY c.id
ORDER BY "lastSeen" DESC NULLS LAST, c."createdAt" DESC;

5. Authentication Flow: Sessions vs JWT

Security is designed with a two-phase roadmap: lightweight, zero-spoofing session tokens today (Phase 1-3), transitioning smoothly to Pi OAuth + JWT in Phase 4.

Phase 1-3: State-Backed Session Token

  • Cryptographically random UUID generated by Node.js crypto.randomUUID()
  • Stored in database Session table
  • Instant revocation capability by deleting DB row
  • No hardcoded or client-side secrets needed

Phase 4: Pi Network OAuth + JWT

  • User logs in via official Pi SDK (Pi.authenticate)
  • Backend validates access token with Pi Core servers
  • Signs stateless JSON Web Token (JWT) with JWT_SECRET
  • Only backend/src/middleware/auth.ts changes; all routes stay identical!

6. Transaction Idempotency & Financial Safety

Financial ledger integrity is paramount. In distributed networks or mobile connections, requests may time out or users might accidentally double-tap the "Send" button. The backend provides strict idempotency guarantees.

Double-Tap & Race Condition Defense

If two identical write requests arrive concurrently within milliseconds:

  1. Both pass the initial findUnique check because neither has committed yet.
  2. One request successfully commits to PostgreSQL.
  3. The second request triggers PostgreSQL's unique constraint on idempotencyKey, causing Prisma to throw error code P2002.
  4. The controller catches P2002, fetches the record created by request #1, and returns 200 OK with idempotent: true. No duplicate debit occurs!

7. Background Jobs (Reconciliation & Maintenance)

Located in backend/src/jobs/reconciliation.ts, a background cron job runs automatically every 5 minutes in production mode.

Job Routine Trigger Interval Actions Performed
Pass 1: Expired Pending Txns Every 5 min (*/5 * * * *) Identifies transactions stuck in pending state where expiresAt < NOW(). Queries the payment gateway/blockchain and moves status to completed or expired.
Pass 2: Late Confirmations Every 5 min (*/5 * * * *) Scans transactions marked expired within the last hour. If the blockchain confirmed late, updates status to completed (resolves edge case V-001).
Session Table Sweeper Every 5 min (*/5 * * * *) Executes prisma.session.deleteMany({ where: { expiresAt: { lt: new Date() } } }) to keep the session table small and fast.

8. Frontend – Backend Integration Bridge

The frontend communicates with the backend through a typed API client: src/lib/api.ts.

// How the frontend makes authenticated requests
import { auth, contactsApi, transactionsApi } from "@/lib/api";

// 1. Login sets session token in localStorage
const { sessionToken } = await usersApi.login("GDEMO123...");
auth.setToken(sessionToken);

// 2. Fetch contacts (automatically appends 'Authorization: Bearer ')
const { data: contacts } = await contactsApi.list();

// 3. Create a transaction with an auto-generated idempotency key
const newTx = await transactionsApi.create({
  description: "Coffee Payment",
  amount: 2.5,
  type: "debit",
  contactId: contacts[0]?.id,
  idempotencyKey: crypto.randomUUID()
});

9. How to Run Locally (Step-by-Step)

Follow these steps to spin up the complete environment on your machine:

1 Start PostgreSQL Service

Ensure PostgreSQL 17 is running on macOS:

# Start postgres service
brew services start postgresql@17

# Alternatively, manual start if brew service fails:
pg_ctl -D /opt/homebrew/var/postgresql@17 -l /opt/homebrew/var/log/postgresql@17.log start

2 Verify Environment Files

Ensure both environment files exist:

Root frontend (.env.local):

VITE_API_URL=http://localhost:3001

Backend (backend/.env):

DATABASE_URL="postgresql://postgres:password@localhost:5432/bookkeeping?connection_limit=5&pool_timeout=10"
PORT=3001
NODE_ENV=development
CORS_ORIGIN="http://localhost:5173,http://localhost:3000"
LOG_LEVEL=info
JWT_SECRET="dev-secret-change-in-phase-4"

3 Run Database Migrations & Seed

cd backend

# Run migrations (creates tables)
npx prisma migrate dev --name init

# (Optional) Seed with sample contacts & transactions
npm run db:seed

4 Start Backend Server (Terminal 1)

cd backend
npm run dev

# Output:
# 🚀 Bookkeeping API running on port 3001 (development)

5 Start Frontend Server (Terminal 2)

# In project root
npm run dev

# Open http://localhost:3000 in your browser

11. API Endpoints Reference

Method Route Auth Description
GET /api/health Public Returns server uptime and database connection status.
GET /api/users/:walletAddress Public Upserts user, creates 24h session, returns sessionToken.
PUT /api/users/:walletAddress Bearer Updates displayName (enforces wallet ownership).
GET /api/contacts Bearer Lists user contacts with aggregated credit/debit totals.
POST /api/contacts Bearer Creates new contact (unique wallet per user).
PUT /api/contacts/:id Bearer Updates contact name or category.
DELETE /api/contacts/:id Bearer Deletes contact (transactions retain contactId=null).
GET /api/transactions Bearer Paginated transaction history with filters (type, contact, dates).
POST /api/transactions Bearer Creates transaction (requires idempotencyKey).
GET /api/transactions/summary Bearer Calculates total credit, total debit, net balance in one query.
GET /api/transactions/contact/:contactId Bearer Fetches ledger statement for a specific contact.
DELETE /api/transactions/:id Bearer Soft-deletes transaction (marks deletedAt).
