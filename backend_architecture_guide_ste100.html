2. System Architecture

The application uses a standard three-tier architecture with separate functional layers:

Layer Primary Files Primary Function
Client src/lib/api.ts, src/App.tsx Controls the user interface. Sends HTTP requests with a stored Bearer token. Logs the user out if an HTTP 401 error occurs.
API Gateway and Middleware backend/src/index.ts, backend/src/middleware/* Applies security headers and CORS rules. Enforces rate limits (100 reads per minute, 30 writes per minute) and payload limits (100 KB). Catches runtime errors.
Authentication Layer backend/src/middleware/auth.ts Extracts the Bearer token from the HTTP request header. Verifies the session in the database and checks expiration. Attaches the user object to the request.
Business Logic backend/src/controllers/* Processes transactions and profile updates. Executes contact calculation queries and validates idempotency keys.
ORM and Database backend/prisma/schema.prisma, backend/src/lib/prisma.ts Defines database models and relation rules. Manages schema migrations and executes parameterized SQL queries.
Background Tasks backend/src/jobs/reconciliation.ts Runs every five minutes. Reconciles pending payment transactions and deletes expired sessions from the database.

3. Request Lifecycle and Code Flow

Each HTTP request follows a defined path from the Express server to the database query and final JSON response.

Architecture Components

  • Application Entry Point (backend/src/index.ts): Initializes the Express application. Loads security middleware, mounts route handlers, and listens on network port 3001. Catches SIGINT and SIGTERM signals for graceful process termination.
  • Configuration Loader (backend/src/lib/config.ts): Verifies required environment variables during startup. The server stops immediately if required variables like DATABASE_URL are missing.
  • Request Validation (backend/src/middleware/validate.ts): Validates request data against Zod schemas. Removes dangerous HTML tags with the xss library to prevent stored Cross-Site Scripting (XSS) attacks.
  • Data Serializers (backend/src/lib/serializers.ts): Converts internal Prisma data objects into standard JSON numbers and strings. This maintains data compatibility with the React frontend.

4. Database Structure and Prisma ORM

The persistence layer uses PostgreSQL and the Prisma 5 Object-Relational Mapper. The database schema maintains data integrity through foreign keys, cascade delete rules, and unique constraints.

Key Database Design Rules

Design Rule Implementation Technical Rationale
Currency Precision Decimal(18, 7) Standard floating-point numbers cause rounding errors. The Decimal(18, 7) type maintains seven exact decimal places for cryptocurrency micro-transactions.
Soft Deletion deletedAt DateTime? When a user deletes a transaction, the database does not remove the row. The system records a timestamp in deletedAt. This action preserves the audit record.
Contact Foreign Key Rule onDelete: SetNull The deletion of a contact does not delete associated transactions. The database sets contactId to null. This rule keeps wallet balance records accurate.
Single-Query Grouping $queryRaw with LEFT JOIN Prevents N+1 database query issues. When listing contacts, the database engine calculates total credits, debits, and latest timestamps in one SQL query.
View Contact Calculation SQL Query OPTIMIZED 
SELECT
  c.id, c.name, c.category, c."piWalletAddress", c."userId",
  c."createdAt", c."updatedAt",
  COALESCE(SUM(CASE WHEN t.type = 'credit' THEN t.amount ELSE 0 END), 0)::float AS "totalCredit",
  COALESCE(SUM(CASE WHEN t.type = 'debit'  THEN t.amount ELSE 0 END), 0)::float AS "totalDebit",
  MAX(t.timestamp) AS "lastSeen"
FROM "Contact" c
LEFT JOIN "Transaction" t
  ON t."contactId" = c.id
  AND t."userId" = ${userId}
  AND t."deletedAt" IS NULL
WHERE c."userId" = ${userId}
GROUP BY c.id
ORDER BY "lastSeen" DESC NULLS LAST, c."createdAt" DESC;

5. Authentication: Sessions and JSON Web Tokens

The authentication architecture includes two implementation phases. Phase 1 through Phase 3 uses database session tokens. Phase 4 will use Pi Network OAuth and JSON Web Tokens (JWT).

Phase 1 to Phase 3: State-Backed Session Tokens

  • Generates a random UUID with Node.js crypto.randomUUID().
  • Stores session records in the database Session table.
  • Enables immediate session revocation by deleting the database record.
  • Requires no client secrets or hard-coded application keys.

Phase 4: Pi Network OAuth and JSON Web Tokens

  • User authenticates through the official Pi SDK (Pi.authenticate).
  • The backend server verifies the access token with Pi Core servers.
  • The server creates a stateless JSON Web Token signed with JWT_SECRET.
  • The authentication middleware changes, but API routes remain unchanged.

6. Transaction Idempotency and Ledger Protection

Financial ledger accuracy is critical. Network timeouts or duplicate user clicks can cause duplicate submissions. The backend system uses idempotency keys to prevent duplicate transactions.

Defense Against Duplicate Submissions and Race Conditions

If two identical write requests arrive at the same time, the server processes them in this sequence:

  1. Both requests pass the initial findUnique query before database write operations start.
  2. The first request successfully commits to the PostgreSQL database.
  3. The second request violates the unique constraint on idempotencyKey. Prisma returns error code P2002.
  4. The transaction controller catches error P2002 and loads the existing transaction record.
  5. The server returns HTTP status 200 OK with the property idempotent: true. Duplicate transactions do not occur.

7. Background Tasks: Reconciliation and Maintenance

The background scheduler in backend/src/jobs/reconciliation.ts runs every five minutes in production mode.

Task Routine Trigger Interval Actions Performed
Pass 1: Expired Pending Transactions Every 5 minutes (*/5 * * * *) Finds transactions in pending status where expiresAt is earlier than current time. Queries the payment gateway and changes status to completed or expired.
Pass 2: Late Confirmations Every 5 minutes (*/5 * * * *) Scans transactions marked expired during the past 60 minutes. If payment confirmation arrived late on the network, updates status to completed.
Session Table Maintenance Every 5 minutes (*/5 * * * *) Runs deleteMany on the Session table for records where expiresAt is earlier than current time. This keeps table size small and search speed fast.

8. Frontend and Backend Integration

The React frontend communicates with the backend API through the typed client module in src/lib/api.ts.

// Example of authenticated API requests from the frontend client
import { auth, contactsApi, transactionsApi, usersApi } from "@/lib/api";

// 1. Connect wallet and save session token
const { sessionToken } = await usersApi.login("GDEMO123...");
auth.setToken(sessionToken);

// 2. Fetch contact records (appends "Authorization: Bearer ")
const { data: contacts } = await contactsApi.list();

// 3. Create a transaction record with a unique idempotency key
const newTransaction = await transactionsApi.create({
  description: "Coffee Payment",
  amount: 2.5,
  type: "debit",
  contactId: contacts[0]?.id,
  idempotencyKey: crypto.randomUUID()
});

9. Procedure: Local Environment Setup

Follow these steps to configure and start the application on a local machine:

1 Start the PostgreSQL Service

Start the PostgreSQL 17 service on macOS:

brew services start postgresql@17
NOTE: If the Homebrew service command fails, start PostgreSQL directly with pg_ctl:
pg_ctl -D /opt/homebrew/var/postgresql@17 -l /opt/homebrew/var/log/postgresql@17.log start

2 Verify Environment Configuration Files

Make sure that both environment configuration files exist in the project:

Frontend environment file (.env.local):

VITE_API_URL=http://localhost:3001

Backend environment file (backend/.env):

DATABASE_URL="postgresql://postgres:password@localhost:5432/bookkeeping?connection_limit=5&pool_timeout=10"
PORT=3001
NODE_ENV=development
CORS_ORIGIN="http://localhost:5173,http://localhost:3000"
LOG_LEVEL=info
JWT_SECRET="dev-secret-change-in-phase-4"

3 Execute Database Migrations and Seed Data

Apply database migrations to create tables. Optionally insert sample records:

cd backend

# Execute database migrations
npx prisma migrate dev --name init

# (Optional) Seed the database with sample data
npm run db:seed

4 Start the Backend Server

Open a terminal window. Start the Node.js backend server:

cd backend
npm run dev

# Console output:
# 🚀 Bookkeeping API running on port 3001 (development)

5 Start the Frontend Application

Open a second terminal window. Start the Vite development server:

# In project root directory
npm run dev

# Open http://localhost:3000 in your web browser

11. API Endpoints Reference

This table lists all available HTTP endpoints in the backend application:

Method Route Authentication Description
GET /api/health Public Returns server uptime and database connection status.
GET /api/users/:walletAddress Public Finds or creates a user. Creates a 24-hour session and returns the session token.
PUT /api/users/:walletAddress Bearer Updates the user display name. Verifies wallet ownership.
GET /api/contacts Bearer Returns user contacts with calculated credit and debit sums.
POST /api/contacts Bearer Creates a new contact record. Verifies unique wallet address per user.
PUT /api/contacts/:id Bearer Updates contact name or category.
DELETE /api/contacts/:id Bearer Deletes the contact. Associated transactions remain with contactId set to null.
GET /api/transactions Bearer Returns paginated transaction records with type, contact, and date filters.
POST /api/transactions Bearer Creates a new transaction. Requires a unique idempotencyKey value.
GET /api/transactions/summary Bearer Calculates total credit, total debit, and net balance in one query.
GET /api/transactions/contact/:contactId Bearer Returns all ledger transactions for a specified contact.
DELETE /api/transactions/:id Bearer Applies soft deletion to the transaction by setting the deletedAt timestamp.
